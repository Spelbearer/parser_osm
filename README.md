# OSM POI: выгрузка и обновление по регионам

Python-процесс для чтения OSM PBF, выделения POI по точным парам ключ/значение, пространственной привязки и сравнения полных снимков. Поддерживаются node, площадные way и multipolygon/boundary relations; есть отдельное правило для линий. Выход: CSV по регионам, дельты и пакетный Parquet, журнал запуска и SQLite-реестр. Стек: Python 3.11, osmium, Shapely, PyArrow, requests и SQLite.

География — международно признанная территория РФ. Категории `commercial`, `food`, `retail`, `coffee` пока выключены; `shop=outpost` включён для пунктов выдачи по запросу адресной программы POI. Производственные полигоны **не включены**: их нужно получить и проверить отдельно. Доступ к Geofabrik и OSM Wiki в облачной среде блокировался прокси, поэтому загрузка актуального PBF всей России и сверка актуальных страниц источников не заявлены как выполненные. Работу программы проверяют воспроизводимые тестовые PBF; реальная региональная и общероссийская приёмка остаются обязательными перед эксплуатацией.

## Установка на Windows

Получите проект:

```powershell
git clone https://github.com/Spelbearer/parser_osm.git
cd parser_osm
```

Из каталога проекта в PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

`requirements-dev.txt` включает рабочие зависимости и pytest; для эксплуатации достаточно `requirements.txt`. Используйте существующий checkout: отдельный Git worktree для запуска не нужен. В облачной/Linux-среде:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Все последующие команды `python` означают Python из этого виртуального окружения. Администраторские права для проекта не нужны. Не отключайте проверку TLS или контрольных сумм при установке/загрузке.

## Воспроизводимый тестовый запуск

На Windows из корня проекта в PowerShell (активация окружения не требуется):

```powershell
.\.venv\Scripts\python.exe scripts/make_demo.py
.\.venv\Scripts\python.exe main.py --config demo/settings.json --mode full
.\.venv\Scripts\python.exe main.py --config demo/settings.json --mode incremental
.\.venv\Scripts\python.exe main.py --config demo/settings.json --check
```

На Linux из корня проекта:

```bash
.venv/bin/python scripts/make_demo.py
.venv/bin/python main.py --config demo/settings.json --mode full
.venv/bin/python main.py --config demo/settings.json --mode incremental
.venv/bin/python main.py --config demo/settings.json --check
```

Демо создаёт маленький локальный PBF и искусственные полигоны. Оно проверяет программный путь от чтения PBF до публикации CSV/Parquet, но не достоверность административных границ. Повторное выполнение на том же снимке не должно давать NEW/UPDATED/DELETED. Тесты также проверяют изменения между снимками и сохранение предыдущего успешного состояния при ошибке.

## Подготовка производственных данных

Если скачаны федеральные округа в `D:\osm_data`, используйте [пакетный сбор России](docs/collection.md):

```powershell
.\.venv\Scripts\python.exe -m poi_osm.collection "D:\osm_data" --output "D:\osm_results" --check
.\.venv\Scripts\python.exe -m poi_osm.collection "D:\osm_data" --output "D:\osm_results"
```

Восемь согласованных округов обрабатываются последовательно с контрольными точками. Итоговые файлы для просмотра находятся в `preview_runs/<run_id>/regions/`, максимум по 50 000 строк; `regions_index.csv` показывает регионы и размеры частей. Крымский extract исключён по выбранному охвату. Первый сбор остаётся предварительным до проверки всех границ; боевой режим `--production` требует подтверждённой полноты и проверенного GeoJSON.

Для первого просмотра **локального регионального PBF**, без настройки производственных границ:

```powershell
.\.venv\Scripts\python.exe -m poi_osm.preview "D:\parser\north-caucasus-fed-district-261108.osm.pbf"
```

Команда не скачивает данные, не изменяет основной реестр и не рассчитывает удаления. Она создаёт отдельный `preview/<run_id>/` с **`poi.csv` — одна строка на OSM-объект**, `poi_objects.parquet`, уникальными региональными CSV в `objects/`, а также детальными данными по тегам (`poi_by_tag.csv`, `full/<код>.csv`, `poi_assigned.parquet`), `review.csv` и `summary.json`. В `poi.csv` все теги и категории объекта объединены, а исходные соответствия сохранены в поле `classifications` (JSON). Статус строк — `PREVIEW`. Кандидаты границ извлекаются из самого PBF и остаются **непроверенными**; если пригодных границ нет, координаты и категории выгружаются без региона. Успешный просмотр не подтверждает полноту регионального снимка или пригодность его границ для регулярного обновления.

Дата снимка читается из заголовка PBF. Если её нет, укажите достоверную дату через `--source-date YYYY-MM-DD`; имя файла само по себе не является проверкой даты. Не используйте частичный PBF как полный снимок России.

Если сборщик не смог создать отдельные площадные POI, пробный режим сохраняет остальные записи, помещает проблемные ID в `review.csv` с причиной `unassembled_geometry` и выставляет **PREVIEW_INCOMPLETE**. Число пропущенных объектов и категорий видно в `summary.json` (`unresolved_objects`, `skipped_poi_records`). Это не полный результат. Обычный FULL/INCREMENTAL продолжает блокировать такие снимки, чтобы отсутствие геометрии не превратилось в ложное удаление.

1. Проверьте разрешённые ключи в `config/tag_mapping.json`. В нём есть исходные 50 значений и дополнительные пары для связи, ремонта и постаматов; `commercial`, `food`, `retail`, `coffee` остаются выключенными. См. [правила категорий и источников](docs/tags-and-sources.md).
2. Получите проверенные региональные полигоны EPSG:4326 в `boundaries/regions.geojson`. В свойствах features нужны коды из `config/regions.json`; источник и `coverage_id` указываются на уровне FeatureCollection. Справочник содержит 83 ISO-кода, а не автомобильные коды. Все коды реестра должны присутствовать в наборе границ. Внешняя граница и отсутствие перекрытий требуют отдельной проверки; см. [географические ограничения](docs/architecture.md).
3. Проверьте `config/settings.json`: источник PBF, контрольную сумму, срок допустимой давности, область покрытия, пороги качества и пути. `project_root` разрешается относительно файла настроек; остальные пути относятся к этому корню. После содержательной проверки границ установите `boundaries_reviewed: true`. Не переключайте этот флаг только для обхода ошибки.
4. Выполните `--check`, затем обработайте один выбранный регион и изучите результат. Для проверки целевого региона всё равно требуются согласованные исходный снимок и геометрические зависимости. Частичный региональный PBF нельзя выдавать за полный снимок России.
5. После проверки одной области выполните полный запуск; сравните статистику и непривязанные объекты перед настройкой расписания.

При желании получить **кандидат** полигонов из текущего PBF:

```bash
python main.py --config config/settings.json --prepare-boundaries boundaries/candidate.geojson
```

Это вспомогательное извлечение административных areas из OSM, а не получение проверенных официальных границ. Кандидат помечается как требующий проверки и намеренно не получает готовый `coverage_id`. Его нельзя напрямую использовать для производственной публикации. Нужно устранить территориальные расхождения, вложенные округа, недостающие коды, проблемы у антимеридиана и задокументировать преобразования.

Примеры производственных команд:

```bash
python main.py --check
python main.py --mode full
python main.py --mode full --force-download
python main.py --mode full --region "Московская область"
python main.py --mode incremental
python main.py --mode full --duplicates
```

`INCREMENTAL` реализован как безопасное сравнение **полных** снимков; replication/diff не применяется. Это требует нового полного PBF, но корректно учитывает удаление категорий и геометрические зависимости. Сетевой источник может быть заменён явным локальным входом с датой, SHA-256, происхождением и подтверждённым полным охватом — поля должны соответствовать проверкам `poi_osm/sources.py`. Не выдумывайте дату актуальности или происхождение файла.

`--check` проверяет конфигурацию, существующие пути/состояние и доступность источника, не загружая PBF и не публикуя данные. Код возврата `0` означает успешную проверку/запуск, ненулевой — ошибку. Для фонового запуска предусмотрен `main.pyw`, сохраняющий этот же код возврата.

## Результаты и история

Основной **`poi.csv` содержит одну строку на пару `(osm_type, osm_id)`**, идентификатор `osm_uid` имеет вид `node/123`. Все категории сохраняются в одной строке, а не удаляются. `poi_objects.parquet` и региональные CSV в `objects/` используют тот же формат. Старые `full/`, `delta/` и `all_russia.parquet` остаются детальными по тегам для сравнения снимков. [Описание формата и преобразование уже готовой выгрузки без PBF](docs/object-export.md).

Для загрузки в Teradata создаются отдельные **`poi_teradata.csv` и `poi_teradata.parquet`**: одна строка на объект, единственные `primary_tag`, `primary_category`, `primary_subcategory`, а все исходные теги — в `all_tags`. Если есть телефония, выбирается она; порядок задаёт `config/primary_selection.json`. Основная категория не входит в ключ MERGE. [Правила и новая схема Teradata](docs/teradata.md).

В файлах Teradata по умолчанию оставлены только **node и way**; relation исключены настройкой `teradata_osm_types` в том же справочнике. Полный реестр, общий `poi.csv` и чтение геометрий/границ сохраняют все типы. В отчёте `teradata_objects` — число строк для загрузки, `teradata_excluded_by_type` — исключённые объекты.

Для адресной программы в каждый CSV/Parquet добавлены `category`, `subcategory`, `is_telecom`, `telecom_type`, `chain_name`, `chain_id`, `is_chain` и поля происхождения классификации. Исходные `tag`, `osm_key`, `osm_value` сохраняются. [Справочники и примеры фильтров](docs/business-filters.md) объясняют, как выделить телефонию и исключить распознанные сети. Новые поля появляются после повторной обработки PBF; существующие CSV автоматически не переписываются.

Все базовые группы и подкатегории редактируются в `config/categories.json`. Отдельный `config/telecom.json` содержит прямые и косвенные направления телефонии; `electronics`, `electronics_repair`, `computer`, `repair` по умолчанию включены в неё с пометкой косвенной связи. Список сетей редактируется в `config/chains.json`. Python-код для изменения этих справочников править не нужно.

Каталоги генерируются относительно `project_root`:

```text
source/                         проверенные исходные PBF и метаданные
work/                           временные данные и этапы незавершённых запусков
output/runs/<run_id>/
    full/<region_code>.csv      CSV: UTF-8 BOM, ;, точка в координатах
    delta/new_poi.csv
    delta/updated_poi.csv
    delta/deleted_poi.csv
    all_russia.parquet          если write_parquet=true
    registry.sqlite            реестр версии, включая состояние удалений
state/last_success.json         указатель на успешную общую версию
state/scopes/<code>/last_success.json  отдельная история регионального запуска
logs/                          журналы с traceback при ошибках
```

Фактические дополнительные отчёты и файлы смотрите в каталоге версии и метаданных запуска. Незавершённый каталог не является опубликованным результатом. Для чтения текущих данных используйте пути из `last_success.json`. Региональный запуск имеет отдельное состояние и не удаляет записи других регионов из общероссийского реестра.

`osm_id` хранится строкой без потери точности. Идентичность объекта определяется парой `osm_type + osm_id`, идентичность экспортируемой строки — тройкой `osm_type + osm_id + tag`. Отсутствующее имя — NULL (пустое поле CSV и null в Parquet), не повод исключать POI. Метаданные включают даты источника/наблюдения/обработки и `NEW`, `UPDATED`, `UNCHANGED`, `DELETED`.

Записи без однозначного региона находятся отдельно в `full/unassigned.csv` и `review.csv`; в общероссийский Parquet они не включаются. Метрики и реестр сохраняют их для контроля качества и безопасного сравнения. Перед загрузкой дельт в Teradata используйте только записи с согласованным `region_code`.

При падении или неуспешном контроле качества предыдущий указатель не меняется. Непривязанные/неоднозначные POI сохраняются для проверки. Резкое сокращение общего или регионального количества блокирует публикацию. `--duplicates` выдаёт кандидатов по расстоянию, имени, категории и адресу; автоматического удаления нет. Размер допустимого расстояния задаётся настройками; решения пользователя нужно хранить отдельно.

## Автоматизация и интеграция

[Планировщик Windows](docs/windows-scheduler.md): ежемесячный запуск, рабочий каталог, возврат ошибки, логи и запуск без окна.

[Teradata](docs/teradata.md): предварительная схема, составной ключ и безопасный MERGE через staging. Подключение к Teradata для автономной выгрузки не требуется; исполняемый загрузчик в СУБД в этот этап не включён.

[Архитектура и ограничения](docs/architecture.md): память, диск, геометрии, область покрытия, повторный запуск и публикация. Нагрузочный тест всей России и проверка на настоящей Windows-машине не заменяются тестами в Linux.

## KML-слои и ZIP

[Формирование KML](docs/kml.md): региональные слои всех названных POI и кругов радиусом 60 м с минимум пятью разными названиями, упаковка проверенного ZIP в заданную папку. Работает из готового production-набора, без PBF и подключения к Teradata. Настройки: `config/kml.json`.

```powershell
.\.venv\Scripts\python.exe -m poi_osm.kml "D:\osm_results\runs\20261111T150943-6d13d9fc" --output "D:\osm_results\kml"
```
