# POI OSM 0.9.0rc4

Кандидат выпуска: сборка POI, актуализация, очистка, CSV/Parquet, KML ZIP и загрузка полного снимка в Teradata.

Один основной скрипт — **`run.py`**. Он обрабатывает согласованный набор PBF, актуализирует реестр, формирует выгрузку POI для Teradata и KML-слои, сохраняет ZIP и удаляет промежуточные данные. Загрузка в Teradata запускается отдельной явной командой `--load-teradata`.

## Новая установка

Запускайте проект из клонированного репозитория с Python 3.11 или 3.13. Установите зависимости из `requirements.txt` в `.venv`. Подготовьте локальный набор PBF и **уже проверенный** полный GeoJSON регионов согласованной территории.

```powershell
.\.venv\Scripts\python.exe run.py --root "D:\osm_results" --init --input "D:\osm_data" --boundaries "D:\approved\regions.geojson"
```

`--init` проверяет набор источников и границы и сохраняет конфигурацию. Затем выполните обычный запуск ниже. Если у вас уже есть готовая production-сборка или компактный `result`, повторная первичная настройка не нужна.

## Переход с существующей структуры

Из `D:\parser\parser_osm` один раз выполните:

```powershell
git pull
.\.venv\Scripts\python.exe run.py --root "D:\osm_results" --adopt
```

Команда использует последнюю успешную production-сборку и проверенные границы. PBF повторно не извлекаются. Создаётся компактный результат, проверяется его целостность, затем удаляются распознанные старые кэши, preview, версии выгрузок и распакованные KML. Исходные PBF сохраняются. После перехода используйте команды `run.py` ниже.

## Обычная работа

Новый снимок данных из папки, заданной в `product.json`:

```powershell
.\.venv\Scripts\python.exe run.py --root "D:\osm_results"
```

Пересоздание файлов из последнего реестра — например, после изменения радиуса кругов, порога плотности или колонок выгрузки:

```powershell
.\.venv\Scripts\python.exe run.py --root "D:\osm_results" --files
```

Этот режим не читает PBF. Кэш частей после завершения обычного запуска удаляется, поэтому новый снимок проходит полное извлечение.

## Что остаётся на диске

```text
D:\osm_results\
    product.json                     пути и правила хранения
    config\                          настройки сборки, KML и колонок Teradata
    boundaries\                      проверенные регионы и полигоны РФ
    logs\                            до 10 журналов; отчёт последней ошибки
    result\
        poi_teradata.csv              18 колонок, одна строка на osm_type + osm_id
        poi_teradata.parquet
        regions\                     CSV по регионам, части до 50 000 строк
        poi_layers.zip               KML внутри архива
        analysis\                    summary, audit, review, индексы и отчёт KML
        .state\                      последний реестр и состояние актуализации
```

Хранится **только последний успешный результат**. Пока новый результат не прошёл проверки, предыдущий сохраняется. Распакованных KML после сохранения и проверки ZIP нет. Временная `.work` существует только во время выполнения; при обычной ошибке она удаляется, после аварийного обрыва очищается при следующем запуске. Журнал публикации защищает предыдущий реестр при сбое замены.

**Для быстрой проверки смотрите `result/analysis/summary.json`.** В `cleanup.json` указано, что удалено и какие неизвестные файлы сохранены. Входные PBF, `.venv`, `.git`, пользовательские файлы и действующий реестр автоматическая очистка не удаляет.

Подробности: [производственный режим и очистка](docs/product.md), [правила KML](docs/kml.md), [колонки Teradata](docs/teradata.md). Модули `poi_osm.*` обслуживают внутренний обработчик и диагностику; обычная работа выполняется через `run.py`. Проверки выпуска описаны в [validation.md](docs/validation.md).

Данные: © OpenStreetMap contributors, [ODbL](https://www.openstreetmap.org/copyright). Для выбранного охвата используются проверенные пользователем границы РФ по международно признанной территории.

## Названия регионов компании

В `config/region_dictionary.json` встроен справочник из `DICTIONARY_V2.xlsx`. Итоговое `region_name` берётся из **EDW**, сопоставление выполняется по ISO-коду. Для Кемеровской области согласовано «Кемерово», для Тывы сохраняется «Хакасия». `FLAG` не является фильтром; макрорегиональные поля сохранены как справочные.

Переименовываются файлы выгрузки и KML, география и состояние актуализации не меняются. Применение к готовым данным — обычный `run.py --root "D:\osm_results" --files`. Сверка доступна в `result/analysis/region_mapping.csv`, параметры и счётчики — в `summary.json`. Для собственного файла задайте `region_dictionary` в `product.json`; без этого используется встроенный JSON проекта. Excel для запуска не требуется.


## Загрузка в Teradata

Целевая таблица — `SBX_OPERATION.DAK_POI_ISH`, сервер — `td2800.corp.tele2.ru`. Установите дополнительные зависимости из `requirements-teradata.txt`. Авторизация LDAP: текущий пользователь `getpass.getuser()`, пароль из `POI_TD_PASSWORD` либо keyring (сервис `teradata`). Пароль в JSON и исходном коде не хранится.

```powershell
.\.venv\Scripts\python.exe run.py --root "D:\osm_results" --check-teradata
.\.venv\Scripts\python.exe run.py --root "D:\osm_results" --load-teradata
```

Первая команда проверяет данные без подключения. Вторая **полностью заменяет содержимое таблицы**: DELETE, INSERT пакетами по 10 000, проверка количества и уникальности, единый COMMIT. При ошибке выполняется ROLLBACK. `OSM_TYPE_ID` формируется как `osm_type/osm_id`. Отчёт — `result/analysis/teradata_load.json`, последний журнал — `logs/teradata.log`. Обычный сбор и `--files` не обращаются к Teradata. Подробности и настройка keyring — в [инструкции](docs/teradata.md).
