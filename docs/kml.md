# KML-слои POI и локальный ZIP

Для обычной работы используйте [единый производственный скрипт run.py](product.md). Описанная ниже команда — самостоятельный вспомогательный экспорт.

Команда использует завершённую внутреннюю сборку или сокращённый пакет Teradata. Подключения к Teradata, чтения PBF и повторного извлечения OSM не требуется.

```powershell
git pull
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m poi_osm.kml "D:\osm_results\runs\20261111T150943-6d13d9fc" --output "D:\osm_results\kml"
```

После завершения в `D:\osm_results\kml` будет новый архив **`poi_layers-<timestamp>-<id>.zip`**. Папка `runs/<id>` содержит только настройки и отчёты; распакованные слои удаляются после проверки и сохранения ZIP; `last_success.json` указывает на последний успешно проверенный архив. Предыдущие ZIP и исходные данные сохраняются. При ошибке сборки не переключается указатель последнего результата. Для вывода можно указать другую доступную папку, в том числе сетевой файловый путь; параметры доступа задаются средствами ОС.

В ZIP входят:

```text
layers/circles/RU-MOW_Москва_001.kml
layers/points/RU-MOW_Москва_001.kml
... по всем выбранным регионам ...
regions_index.csv
config.json
summary.json
```

Распакуйте ZIP и откройте KML нужного региона в QGIS, Google Earth или другом приложении с поддержкой KML 2.2. При превышении лимита создаются следующие части `_002`, `_003` и т. д. Регионы без подходящих кругов получают корректный пустой KML; счётчики указаны в индексе. Пакет не содержит общего KML, который одновременно загружает все регионы.

## Правила по образцу ins_1308.ipynb

- Вход — существующий `poi_teradata.csv` с одной строкой на `(osm_type, osm_id)`. Ключи проверяются на уникальность; node и way с одинаковым числом сохраняются отдельно.
- По умолчанию используются node и way с непустыми названиями и определённым регионом. Данные без названия не участвуют ни в круге, ни в подсчёте. Непривязанные объекты по умолчанию остаются в исходной выгрузке; их включение в KML настраивается.
- Вокруг каждого уникального положения POI в регионе рассматривается круг **радиусом 60 метров**. Совпадающие центры объединяются, сами объекты сохраняются.
- Круг проходит отбор при **минимум пяти разных названиях** внутри радиуса. Центр тоже учитывается. Имена сравниваются с учётом регистра, после удаления пробелов по краям. Пять объектов одной сети с одним названием дают одно различное название.
- **Отдельный слой точек содержит все названные объекты выбранного набора**, включая одиночные точки вне подходящих кругов. Это согласованный пользователем режим `all_named`.
- Соседние круги могут перекрываться; в общие зоны они не объединяются. Круги не обрезаются границами регионов; точки соседнего региона в пределах радиуса тоже участвуют в подсчёте. Сам круг записывается в регион центра, точка — в собственный регион.
- В нашем наборе нет макрорегионального справочника ноутбука; файлы группируются по коду и названию субъекта РФ.

Расстояния и вершины кругов рассчитываются по эллипсоиду **WGS84** через `pyproj.Geod`. Координаты центров не округляются до трёх знаков. Точки проверяются по точному геодезическому расстоянию `< radius_m`, а не по приближённому многоугольнику. По умолчанию круг рисуется полигоном из 72 вершин; максимальное отклонение хорды при радиусе 60 м составляет примерно 6 см. Геометрия при пересечении ±180° разделяется на части, чтобы не рисовать полосу через всю карту. Области около географических полюсов выше 89,9° не поддерживаются и вызывают явную ошибку.

В слоях точек сохраняются OSM-идентификаторы, категория/подкатегория, телефония, признаки и название сети, адрес при наличии в источнике. При чтении сокращённого пакета адрес отсутствует, поскольку исключён из его схемы; для наиболее полного KML используйте внутреннюю папку `runs/<run_id>`. Телефония выделена зелёными маркерами, остальные точки — синими; круги имеют полупрозрачную оранжевую заливку. Атрибуты помещаются в ExtendedData, текст и спецсимволы XML экранируются.

## Настройки

Файл **`config/kml.json`** можно редактировать и передавать отдельной копией через `--config`.

| Параметр | По умолчанию | Значение |
|---|---|---|
| radius_m | 60 | Радиус в метрах, от >0 до 10 000 |
| min_count | 5 | Минимум для отбора круга |
| count_mode | distinct_names | Считать разные названия; `objects` считает уникальные объекты |
| points_scope | all_named | Все подходящие названные точки; `selected_circles` — только внутри прошедших кругов |
| circle_vertices | 72 | Число вершин изображаемого круга |
| max_features_per_file | 10000 | Максимум объектов в одной части KML |
| osm_types | node, way | Типы объектов, уже присутствующие в источнике |
| include_unassigned | false | Включать непривязанные точки в отдельные слои |
| telecom_only | false | Оставлять только объекты с is_telecom=1 |
| exclude_chains | false | Исключать объекты с is_chain=1; неизвестная сеть остаётся |
| regions | null | Все регионы; пример ограничения: `["RU-MOW", "RU-MOS"]` |

Фильтры применяются **до** расчёта плотности. Например, `telecom_only: true` строит круги по скоплениям телефонии, а не просто меняет видимость точек после подсчёта.

## Проверки и ресурсы

Отчёт содержит числа исходных, исключённых и экспортированных POI, центров, кругов и файлов. Созданные KML проверяются потоковым XML-разбором и пересчётом Placemark. ZIP проверяется по CRC и составу перед публикацией. В архив попадают только относительные пути слоёв/отчётов; временный SQLite не включается. Статус успеха — `KML_EXPORT_SUCCESS`, `file_checks_ok: true`.

Полные свойства POI хранятся во временном SQLite на диске вывода; координаты, коды названий и пространственный STRtree находятся в памяти. Поиск соседей использует пространственный индекс и точную проверку расстояния. Списки всех пар точек не материализуются, но очень плотные скопления требуют больше сравнений. Временный SQLite удаляется после успешной сборки. При обработанной ошибке временная папка удаляется, короткий отчёт сохраняется в `last_failure.json`. Для явной отладки можно добавить `--keep-unpacked`; производственный `run.py` этот режим не использует.

Проверено на синтетических данных, настоящем маленьком PBF проекта и сокращённом пакете: разные названия/объекты, все названные точки, совпадающие центры, граница радиуса, ±180°, бизнес-фильтры, разбиение KML, XML и ZIP, сохранение предыдущего результата при ошибке. Нагрузочная проверка на 10 000 точек и 10 000 кругов в облачном Linux заняла около 8 секунд с пиком памяти около 68 МиБ; это не замер полного российского набора на пользовательском Windows.
