# Архитектура и границы применимости

## Данные и ресурсы

Процесс читает PBF последовательно через `osmium` (пакет Python для pyosmium/libosmium). Весь PBF и все POI не загружаются в DataFrame. Координаты узлов, необходимые для ways и relations, индексируются на диске. Shapely выполняет геометрические операции и поиск региона через пространственный индекс; GeoPandas и Pandas для этого не требуются. SQLite хранит промежуточный реестр и выполняет сравнение по ключу `(osm_type, osm_id, tag)`. PyArrow записывает Parquet пакетами. В памяти находятся геометрии регионов, текущая геометрия OSM и ограниченный пакет выходных строк.

Ограничение: очень большая отдельная relation всё же требует памяти пропорционально своей геометрии. Внутренний сборщик areas libosmium также хранит в памяти метаданные отобранных по тегам multipolygon relations; его память не ограничена размером выходного пакета. Поэтому постоянный верхний предел RAM не гарантируется, хотя исходный PBF, POI и индекс узлов не загружаются целиком в RAM. Пропускать повреждённую геометрию и затем объявлять отсутствующие POI удалёнными нельзя: ошибка обязательного этапа блокирует публикацию.

Размер текущего общероссийского PBF не измерен: доступ к Geofabrik в среде разработки блокировался сетевой политикой. Поэтому нельзя честно назвать проверенные требования к диску или время обработки всей России. Перед запуском измерьте `Content-Length`, число узлов и пиковый расход ресурсов на представительном региональном снимке. Для дискового индекса нужна память на диске как минимум порядка 16 байт на индексируемый узел плюс служебные расходы реализации; проверьте фактический файл индекса на своей версии osmium. Дополнительно нужны PBF, незавершённая загрузка, новый SQLite/Parquet/CSV и сохранённые предыдущие версии. Сумма файлов двух поколений — нижняя граница, не гарантия достаточного места. Планируйте свободный SSD с запасом и контролируйте размер `work/`.

Начальный ориентир для испытаний на обычном компьютере — 8–16 ГБ RAM и SSD; это рекомендация для измерения, а не результат общероссийского нагрузочного теста. Производительность зависит прежде всего от PBF, диска и сложности relations. Реальный срок следует оценивать по измеренным секунд/ГБ и POI/с на машине запуска, отдельно учитывая повторное чтение для сборки areas и построения границ. Такой пересчёт остаётся оценкой: геометрическая сложность регионов различается.

## Геометрия

* Node сохраняет исходную пару `(lon, lat)`.
* Площадные way и multipolygon/boundary relations получают `representative_point()`: точка должна принадлежать геометрии.
* Линии получают середину по длине геометрии согласно политике конфигурации. Это середина линии в координатах EPSG:4326, а не геодезическое расстояние в метрах.
* Все экспортируемые точки имеют EPSG:4326. WKT записывается как `POINT (longitude latitude)`.

Для локальных POI, пересекающих ±180°, долготы сначала разворачиваются в непрерывный интервал; после выбора внутренней/средней точки её долгота возвращается в [-180, 180]. Непривязанные записи сохраняются в реестре и `full/unassigned.csv` для проверки; они не включаются в `all_russia.parquet` и не получают утверждённую страну. Это позволяет не объявлять ранее встречавшийся объект удалённым из-за проблемы привязки. Метрика `total` включает карантинные записи, поэтому может отличаться от числа строк в общероссийском Parquet.

Не каждую relation можно разумно превратить в POI: route, site и другие составные типы требуют согласованной геометрической семантики. Поддержка node, way и multipolygon не означает, что любая произвольная relation получает корректную точку. Поведение неподдерживаемых целевых relations смотрите в журнале и тестах; такие ошибки нельзя использовать как основание для DELETED.

## Регионы и выбранная территория

`config/regions.json` содержит 83 кода ISO 3166-2:RU и русские названия; `region_id` равен этому же стабильному коду. Это справочник идентичности субъектов, а не географические границы и не автомобильные коды. Ссылка на первоисточник кодов: [ISO OBP](https://www.iso.org/obp/ui/#iso:code:3166:RU). Актуальность страницы в среде разработки проверить не удалось.

Пользователь выбрал международно признанную территорию РФ. Крым, Севастополь и другие территории Украины не включены в справочник. Наличие кода субъекта в справочнике само по себе не определяет внешнюю границу; для других территориальных расхождений источников необходима проверка полигонов в рамках выбранной политики. Нельзя автоматически считать контур Geofabrik или OSM согласованной государственной границей.

Производственный `boundaries/regions.geojson` должен быть проверенным набором неперекрывающихся Polygon/MultiPolygon в WGS84. В FeatureCollection нужны `source` (происхождение, версия/дата, условия использования) и `coverage_id`, совпадающий с реестром; в свойствах каждой feature — `region_code`. Поля имён берутся из реестра. Геометрия субъекта, включающая автономный округ, должна быть приведена к неперекрывающемуся разделению: Тюменская область отдельно от ХМАО/ЯНАО, Архангельская отдельно от НАО. Для геометрий у 180-го меридиана нужна корректная разбивка, чтобы прямой сегмент не пересёк весь мир.

Пример структуры (координаты здесь намеренно не приведены):

```json
{
  "type": "FeatureCollection",
  "source": "Источник границ; дата; ссылка; лицензия; выполненные преобразования",
  "coverage_id": "ru-internationally-recognized",
  "features": [
    {
      "type": "Feature",
      "properties": {"region_code": "RU-MOW"},
      "geometry": {"type": "MultiPolygon", "coordinates": []}
    }
  ]
}
```

Пустые координаты в этом фрагменте — описание схемы, не рабочий набор границ. Подменять реальные границы прямоугольниками нельзя. Тестовые геометрии тестового режима искусственные и не предназначены для географической аналитики.

Точка, попавшая сразу в несколько полигонов (включая общую границу), не получает произвольный первый регион. Неоднозначные и непривязанные объекты выносятся на проверку. Доля таких объектов и правила контроля публикации задаются в конфигурации. Набор границ, источник PBF, справочник и фильтры должны описывать один согласованный охват.

## Обновление и публикация

`FULL` извлекает полный снимок. `INCREMENTAL` в этой реализации также обрабатывает полный снимок и рассчитывает разницу; OSM replication/diff не заявлены как реализованные. Ежемесячный полный пересчёт выбран согласно допустимому варианту ТЗ, поскольку удаление участника way или изменение геометрии relation затрагивает зависимые объекты.

Изменения сравниваются по содержательным полям, а не по дате запуска. Один объект с несколькими категориями образует несколько строк; одинаковый числовой ID у node и way относится к разным объектам. `NEW` впервые появляется в реестре, `UPDATED` меняет содержательные поля, `UNCHANGED` сохраняет их, `DELETED` присутствовал в предыдущем успешном согласованном снимке и отсутствует в новом полном снимке. Отсутствие записи при неудавшейся обработке не является удалением.

Каждый успешный запуск получает отдельный каталог. Старые каталоги сохраняются, указатель `last_success.json` меняется атомарно после завершения всех обязательных проверок. Потребители должны читать каталог из этого указателя, а не выбирать по имени последний созданный каталог. Файл внутри `work/` или неподтверждённая версия `output/` не является опубликованным результатом.

Перезапуск после сбоя повторно использует проверенный исходный файл, но не заявляет побайтовое продолжение работы парсера с места падения. Завершённые публикации сохраняют историю; незавершённые рабочие материалы оставляются для диагностики. Смена области покрытия, состава тегов или границ требует нового согласованного базового состояния, а не автоматического удаления записей из старой области.

Защита от двух копий процесса должна использовать один общий каталог состояния. Две разные конфигурации с разными каталогами состояния не разделяют блокировку. На сетевых файловых системах семантику блокировок и атомарного переименования нужно проверить отдельно; основной сценарий — локальный диск Windows/Linux.

## Проверки и известные ограничения

Проверки включают ключи, категории, WKT, допустимость координат, технические дубликаты, доли отсутствующих названий/регионов, резкое сокращение общего количества и отдельных регионов. Снижение выше порога блокирует публикацию и требует анализа источника и границ. Порог не следует отключать только для получения успешного кода возврата.

Предполагаемые географические дубли — отдельные кандидаты для ручного решения. Совпадение названия и близость точек не доказывают, что это один бизнес: возможны магазины на разных этажах. Автоматическое физическое удаление таких строк не выполняется. Для принятых решений сохраняйте отдельную таблицу: исходные ключи обеих строк, решение, автор, время и обоснование.

В среде разработки не выполнялись загрузка и обработка всей России, проверка реальных административных границ и запуск Планировщика Windows. Успешные локальные тесты проверяют программную реализацию и не заменяют эти приёмочные испытания. Логи и отчёт тестов должны использоваться как фактический список выполненных проверок.
