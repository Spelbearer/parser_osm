# Устройство производственной сборки

Вход приложения — `run.py`. Настройки и проверенные границы размещаются один раз, результат последнего успешного запуска — в `result`. Поддерживаются CPython 3.11 и 3.13, Windows и Linux.

## Обработка снимка

1. Проверяются восемь локальных PBF: состав набора, SHA-256, контрольная сумма издателя при наличии, дата и replication timestamp. Крымский extract исключён выбранным профилем международно признанной территории РФ. Название файла не является источником даты снимка.
2. Каждая часть читается в отдельном процессе pyosmium. Объекты фильтруются по точным парам ключ/значение. Дисковый индекс узлов и служебный SQLite находятся во временной папке; завершение процесса освобождает Windows-дескрипторы libosmium.
3. Технические повторы между частями объединяются по `(osm_type, osm_id, tag)` с проверкой содержимого. Конфликтующие версии не выбираются произвольно. Полный набор пространственно привязывается к проверенным полигонам субъектов.
4. Новый реестр сравнивается с предыдущим: NEW, UPDATED, UNCHANGED, DELETED. Сохраняются first_seen_date, отпечатки и tombstones. Контроль качества блокирует аномальное падение общего/регионального количества и превышение доли непривязанных объектов.
5. Из реестра один раз строится канонический источник одной строки на объект. Приоритет основной категории и проекция создают финальные CSV/Parquet из 17 колонок; отдельно строятся региональные файлы, KML и ZIP.
6. После аудита файлов и проверки ZIP весь `result` заменяется. Временные данные и предыдущий результат удаляются; журнал замены защищает реестр при сбое.

Данные не собираются в единый pandas DataFrame. Реестр, объединение частей и проверка уникальности используют SQLite. KML хранит координаты и пространственный индекс в памяти, свойства точек — во временном SQLite.

## Геометрии

Node использует исходные координаты. Для площадей выбирается внутренняя representative_point, для линий — midpoint или отказ по `line_policy`. Relations читаются для геометрий и границ, но по согласованному выходному профилю не попадают в файлы загрузки.

Полигоны и точки при переходе через ±180° нормализуются. Границы валидируются как WGS84 Polygon/MultiPolygon со всеми кодами из справочника. На стыке нескольких регионов или вне полигонов назначение не угадывается: запись остаётся непривязанной и попадает в review. В общей выгрузке такие объекты сохраняются с пустым регионом; KML по умолчанию их исключает.

Изменение категории не меняет идентификатор объекта. Числовые ID node и way могут совпадать, поэтому ключ результата — `(osm_type, osm_id)`.

## Состояние и совместимость

Формат состояния версии 1 и структура реестра сохраняются в выпуске 0.9.0rc1. Смена путей к копиям тех же проверенных границ не меняет контракт. Изменение самого охвата или правил извлечения требует отдельного baseline.

`--files` применяет приоритеты основной категории, состав колонок и правила KML без чтения PBF и без изменения состояния сравнения снимков. В нём не пересчитывается классификация исходных тегов: для этого нужен обычный запуск.

Переход `--adopt` — единственный сохранённый адаптер к прежней структуре. Он нужен пользователям с уже выполненной production-сборкой. `--init` создаёт новую установку из проверенного GeoJSON и локального набора PBF.

Модули `collection`/`collection_worker` — внутренний обработчик и его процесс-исполнитель. Кандидаты границ и восстановление геометрии остаются вспомогательной диагностикой. Обычный продукт запускается только через `run.py`. Автоматическое скачивание PBF и загрузка в Teradata не входят в этот производственный сценарий.
