# Набор федеральных округов: сбор по всей России

Команда `python -m poi_osm.collection` обрабатывает локальные PBF последовательно, по одному в отдельном процессе. После завершения файла закрываются native-дескрипторы libosmium; это важно для Windows и большого набора. Завершённые промежуточные результаты проверяются хешами и повторно используются после сбоя. Это повторение по этапам, не продолжение с байта внутри незавершённого PBF.

## Входные файлы

По умолчанию нужны восемь файлов из `config/collection.json`: central, far-eastern, north-caucasus, northwestern, siberian, south, ural, volga с суффиксом `-fed-district-YYMMDD.osm.pbf` или `-latest.osm.pbf`. `crimean-fed-district` исключён по ранее выбранному охвату международно признанной территории РФ. Не смешивайте в каталоге общероссийский PBF и региональные части, несколько дат одного округа или неизвестные extracts: команда остановится с объяснением.

На каждый файл вычисляется SHA-256, читается дата снимка из PBF и проверяется давность (по умолчанию 45 дней). Даты и присутствующие replication timestamps должны совпадать между частями. Имя файла не подтверждает дату/полноту/происхождение. Если рядом есть `<имя>.osm.pbf.md5`, проверяется и он; при несовпадении запуск останавливается. По присланным размерам восемь включённых файлов занимают 4 151 388 896 байт (3,87 GiB); крымский файл в эту сумму не входит.

## Первый общероссийский контрольный запуск на Windows

Из каталога репозитория:

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m poi_osm.collection "D:\osm_data" --output "D:\osm_results" --check
.\.venv\Scripts\python.exe -m poi_osm.collection "D:\osm_data" --output "D:\osm_results"
```

`--check` только проверяет входные файлы и ничего не создаёт; INPUT_CHECKED означает проверку входа, а не готовность к боевой публикации. Внешние скачивания и Teradata не требуются. Для файлов без даты в заголовке можно передать достоверную `--source-date YYYY-MM-DD`; даты не выдумываются по имени.

Обычный запуск делает полный предварительный сбор. Ожидаемый результат — `COLLECTION_PREVIEW_SUCCESS` либо `COLLECTION_PREVIEW_INCOMPLETE`. Это реальные POI, но извлечённые из OSM границы остаются непроверенными; такой запуск не обновляет `state/last_success.json` и не рассчитывает удаления. Неполнота явно отмечается при недостающих границах, неразрешённых геометриях или превышении порога непривязанных объектов.

Для результата создаётся новая папка `D:\osm_results\preview_runs\<run_id>`. При повторении команды готовые части с теми же хешами/правилами переиспользуются. Файлы с другим содержимым, повреждённый кэш или изменённые правила извлечения требуют повторной обработки соответствующей части. Изменения приоритетов Teradata и размера CSV-частей не требуют повторного чтения PBF. Ctrl+C останавливает запущенный дочерний процесс и сохраняет завершённые этапы.

## Какие файлы открывать

- **`regions/`** — CSV для Teradata по субъектам РФ с одним объектом на строку и выбранной основной категорией, только node и way. Файлы имеют русское название региона и код. Большие регионы разбиты на части максимум по **50 000 строк данных**.
- **`regions_index.csv`** — небольшой каталог: регион, путь к каждой части, число строк. Его удобно открыть первым. Регионы без найденных точек получают файл только с заголовком.
- `summary.json` — общий статус, входные хеши, сколько частей взято из кэша, дубли между extracts, отсутствующие/конфликтующие коды границ, счётчики POI и список файлов.
- `review.csv` — неразрешённые геометрии и непривязанные/неоднозначные точки.
- `candidate_boundaries.geojson`, `candidate_regions.json` — общий кандидат региональных границ для проверки. Не считать его официально проверенными границами.
- `poi_teradata.csv/parquet` — единый объектный файл России; для просмотра в Excel лучше региональные части.
- `poi.csv`, `objects/`, `full/`, SQLite — полный объектный/детальный набор и служебное состояние, включая relations. Relations исключаются только из файлов Teradata.

Размер частей задаётся `max_rows_per_region_file` в `config/collection.json` (от 1 до 1 000 000 строк без заголовка). Максимальный размер каждой части проверяется при создании. Формат CSV: UTF-8 BOM, `;`, корректное экранирование. Разбиение уменьшает размер открываемого файла; конкретная скорость Excel зависит от компьютера.

## Пересечения extracts и границы

В каждом источнике сначала извлекаются POI без назначения региона. После объединения кандидатов (или чтения проверенного GeoJSON) все точки пространственно привязываются заново в единой системе границ. Поэтому объект на стыке источников не получает разные регионы из-за состава соседнего extract.

Идентичные повторения `(osm_type, osm_id, tag)` между файлами удаляются. Для объекта проверяется согласованность всего набора выбранных категорий и их содержания; противоречащие версии одного объекта блокируют сбор вместо произвольного объединения. В окончательном файле Teradata ключ `(osm_type, osm_id)` уникален.

Кандидаты границ сопоставляются со справочником регионов; неизвестные коды исключаются, разные полигоны одного кода показываются как конфликт. Для неперекрывающегося деления Тюменской области вычитаются ХМАО/ЯНАО, Архангельской — НАО. Пересечения ±180° разбиваются на части. Преобразования документируются в отчёте и требуют проверки. Наличие всех 83 кодов само по себе не доказывает согласованность внешней границы или полноту POI.

## Боевой режим и ежемесячная актуализация

`--production` доступен после проверки границ и полноты набора. Требуются:

1. Проверенный GeoJSON всех кодов из `config/regions.json`, с согласованным `coverage_id` и источником. Сохраните его отдельно от неизменяемых результатов preview, например в `D:/osm_results/approved/regions.geojson`.
2. В settings: путь `boundaries` к этому файлу, `boundaries_reviewed: true` и подтверждённый `coverage_confirmed`. Остальные пути оставьте корректными относительно `project_root`; выходная папка коллекции задаётся `--output`, её не нужно подставлять в project_root.
3. В профиле `config/collection.json`: `complete_snapshot_confirmed: true` после проверки происхождения/охвата согласованного набора. Не включайте флаги только для обхода ошибки.

```powershell
.\.venv\Scripts\python.exe -m poi_osm.collection "D:\osm_data" --output "D:\osm_results" --production
```

Боевой режим использует проверенный набор границ, отвергает неразрешённые геометрии, проверяет падение общего/регионального количества и сравнивает с предыдущей успешной версией. При ошибке предыдущая публикация сохраняется. Результаты размещаются в `runs/<run_id>`, а `state/last_success.json` переключается только после проверки всех файлов. Не запускайте два экземпляра на один output: применяется общая блокировка.

Для месячного обновления замените все восемь частей согласованным новым снимком (по одному файлу на округ) и выполните ту же команду. Это полное сравнение снимков; replication diff не применяется. Категорийные удаления считаются после успешной обработки всей коллекции. Объектный загрузчик Teradata с удалениями всё ещё отдельная задача: отсутствие точки в произвольном staging не удаляет её автоматически.

## Ресурсы и ограничения проверки

PBF, все POI и все узлы не загружаются в единый DataFrame. Дисковые индексы находятся на диске output, а не обязательно на системном C:. Нужен запас места под самый большой индекс, кэш частей, SQLite, CSV/Parquet и предыдущие версии; это больше размера входных PBF. В журнале печатаются входные размеры и свободное место. Старые версии/кэш автоматически не удаляются.

Время и пиковая RAM на реальных восьми файлах пока не измерены. Внутренние структуры сборщика areas и отдельные крупные геометрии требуют памяти сверх выходного пакета. Последовательные процессы снижают пик и освобождают native-ресурсы между PBF. Во время чтения каждых миллиона узлов выводится прогресс. Для первого запуска нужен длительный непрерывный сеанс с SSD и достаточным свободным местом; конкретную длительность покажут журналы на вашем компьютере.

Пакетный путь проверен на настоящих маленьких PBF с синтетическими регионами: склейка пересечений, блокировка конфликтных версий, кэш/повторный запуск, безопасное сравнение снимков, отказ до подтверждения границ, части CSV, даталайн и остановка дочернего процесса. Это не общероссийский нагрузочный тест и не подтверждение реальных границ.

## Проверка большого результата без отправки CSV

Из папки репозитория после `git pull` запустите проверку **папки завершённого запуска**:

```powershell
$run = "D:\osm_results\preview_runs\<run_id>"
.\.venv\Scripts\python.exe -m poi_osm.audit $run --output-dir "D:\osm_results\checks"
```

Команда читает `poi_teradata.csv`, `regions_index.csv` и все перечисленные региональные части. Проверяет уникальность **пары** `(osm_type, osm_id)`, координаты и POINT WKT, включение основной категории в `all_tags`, формат флага телефонии, совпадение счётчиков и каждой строки региональных частей с общим CSV. Числовые ID node и way могут совпадать: это разные объекты. Список ошибок ограничен 50 примерами, общие счётчики ошибок полные. Временный SQLite для ключей находится на диске `--output-dir` и удаляется при завершении. Память не зависит от числа всех объектов; большой CSV не загружается целиком.

В `checks` появится небольшой `audit-<timestamp>-<id>.json`, который можно прислать вместо CSV. `file_checks_ok: true` означает согласованность проверенных файлов. Это **не подтверждение полноты покрытия**, достоверности POI или правильности приоритетов относительно исходного реестра. Preview остаётся preview; `production_ready` для него false. При нарушениях CSV команда завершится с кодом 1, но сохранит отчёт. Ошибки чтения входных файлов прервут проверку.

Если отсутствуют границы Кировской области, Красноярского края или Тюменской области, дополнительно:

```powershell
.\.venv\Scripts\python.exe -m poi_osm.boundary_diagnostics $run --output-dir "D:\osm_results\checks"
```

Команда сверяет SHA-256 исходных PBF с отчётом и читает только relations из соответствующих федеральных округов. При неизвестном отсутствующем коде проверяет все источники. В `boundary-diagnostics-<timestamp>-<id>.json` сохраняются теги административных relations уровня 4, relations с отсутствующими ISO-кодами и подходящими именами, а также числа участников. Это помогает отличить отсутствие нужных тегов от необходимости отдельно исследовать сборку геометрии. Геометрии и границы, описанные только ways, этим отчётом не проверяются; принадлежность непривязанных точек автоматически не угадывается.

Обе команды читают существующие результаты и PBF, пишут только новые отчёты и временный индекс в `checks`. Они не запускают извлечение POI, не переключают состояние публикации и не меняют контракт кэша восьми частей. Полный запуск collection для этих проверок повторять не требуется.

### Восстановление недостающих границ из соседних extracts

Если relations регионов присутствуют и имеют правильные теги, но полигонов нет, выполните:

```powershell
$run = "D:\osm_results\preview_runs\<run_id>"
.\.venv\Scripts\python.exe -m poi_osm.boundary_recovery $run --output-dir "D:\osm_results\checks"
```

В новой папке `checks/boundary-recovery-<timestamp>-<id>/` появятся `report.json`, `candidate.geojson` и небольшой `boundary-subset.osm.pbf`. Команда сверяет SHA-256 со снимком, находит relations отсутствующих субъектов, затем объединяет их геометрические ways и nodes из **всех согласованных источников**. Это несколько последовательных чтений PBF, а не повторное извлечение POI. Выводится прогресс по файлам и этапам. Фильтры ID работают внутри libosmium: Python получает только нужные элементы границ. В памяти хранятся элементы выбранных границ, а не все узлы России; индекс координат создаётся только для небольшого итогового PBF в памяти, без временного `.idx`.

Члены `subarea`, `admin_centre` и `label` не являются контурами. Вложенные relations с геометрическими ролями `outer`/`inner` или пустой ролью пока явно отклоняются. Конфликтующие версии элементов из разных extracts прерывают команду. При недостающих ways/nodes или незамкнутом контуре полигон не создаётся, даже если libosmium мог бы выдать частичную геометрию.

В `report.json` для каждого региона указаны результат сборки, числа и до 100 примеров недостающих элементов/незамкнутых узлов. `RECOVERED_CANDIDATE` означает полученный **непроверенный** полигон. `INCOMPLETE_SOURCE_GEOMETRY` означает нехватку элементов даже после объединения источников; дальнейшее получение полной границы — отдельный шаг. Другие статусы отличают отсутствие relation, разрывы колец, неподдерживаемых геометрических участников и ошибки сборки. Восстановленная граница требует проверки перед использованием в production.

Команда не меняет исходные результаты, рабочий кэш, региональную привязку и состояние production. Пришлите `report.json`, чтобы выбрать следующий шаг. Саму `collection` до проверки этого отчёта повторять не требуется.
