# План интеграции с Teradata

SQL-пример использует подробный формат по тегам из `full/` и `delta/`. Основной `poi.csv` теперь содержит одну строку на объект и объединённые категории; для его загрузки потребуется отдельная схема с ключом `(osm_type, osm_id)` и обработкой `classifications`. Не загружайте объединённое поле `tag` как один исходный OSM-тег в старую таблицу.

Автономная выгрузка не требует Teradata. Этот документ и SQL — проект следующего этапа, а не утверждение, что соединение или SQL проверены на конкретном кластере. Перед применением DBA должен проверить кодировки, лимиты длины, версии SQL, права и распределение данных. Значения не следует молча обрезать при загрузке.

Идентификатор хранится как строка. Логический ключ: `(OSM_TYPE, OSM_ID, TAG)`, поскольку числовые ID могут совпадать между node/way/relation, а один объект имеет несколько категорий. Предлагается UNIQUE PRIMARY INDEX на той же тройке. Это одновременно предотвращает технические дубли и даёт ключ для MERGE. Эффективность распределения требуется измерить на реальном наборе; географический код не подходит как единственный PI из-за перекоса по крупным регионам.

Файл [teradata.sql](teradata.sql) показывает таблицу текущего состояния и MERGE. Staging должен содержать только проверенный запуск и не более одной строки на составной ключ. Загружайте NEW/UPDATED/DELETED из опубликованной дельты либо полный успешный снимок с корректно подготовленными статусами. Наличие строки `DELETED` означает логическое удаление; строка в основной таблице сохраняется с этим статусом. Отсутствие ключа в staging ничего не удаляет.

В рекомендуемом процессе загрузки:

1. Прочитать атомарный указатель успешной версии и сохранить `run_id` с областью покрытия в журнал загрузок.
2. Заполнить отдельную staging-таблицу, проверить уникальность ключей, число записей и принадлежность конкретному опубликованному запуску.
3. В транзакции добавить дельту в append-only историю с `run_id`, выполнить MERGE текущего состояния и отметить этот `run_id` успешно загруженным.
4. Повтор того же `run_id` распознать как уже обработанный. При сбое выполнить rollback и повторить этот же согласованный запуск.

Для истории нужна отдельная таблица с ключом `(RUN_ID, OSM_TYPE, OSM_ID, TAG)`; версия и события не должны теряться при обновлении текущей строки. Простое сохранение DELETED в текущей таблице не заменяет историю всех изменений. По мере роста используйте согласованную политику хранения и партиционирования.

Не используйте `DELETE ... WHERE key NOT IN staging`: региональный или частичный набор привёл бы к удалению объектов всей страны. Не считайте отсутствие объекта в незавершённой выгрузке удалением. Удаления должны приходить из дельты, рассчитанной после успешной полной обработки согласованной области.
