# Подготовка выгрузки для Teradata

Файлы **`poi_teradata.csv`** и **`poi_teradata.parquet`** содержат одну строку на `(osm_type, osm_id)` и одну основную категорию. Они формируются при FULL/INCREMENTAL/preview и при преобразовании готового реестра через `python -m poi_osm.objects`. Само соединение с Teradata и загрузчик пока не реализованы; SQL-пример нужно проверить DBA на целевой версии СУБД.

В выгрузку для Teradata включаются только **node и way**. Relation исключены по согласованному решению; это выходной фильтр, а не удаление из исходного PBF или состояния. Relations продолжают читаться для геометрий, границ и полного реестра. Общие `poi.csv`, `poi_objects.parquet`, `objects/` остаются полными. Настройка в `config/primary_selection.json`: `"teradata_osm_types": ["node", "way"]`. При необходимости relation можно явно вернуть в список и пересоздать экспорт из сохранённого SQLite, без PBF.

Счётчики `unique_objects`/`metrics.unique_objects` относятся к полному набору. Для размера файла загрузки используйте `object_export.teradata_objects` (в отчёте преобразования — `teradata_objects`), а пропуски видны в `teradata_excluded_by_type`. Пустой файл Teradata с заголовком и схемой корректен, если в источнике были только исключённые типы. Если relations уже были загружены в СУБД, новый фильтр их автоматически не удалит: потребуется отдельная согласованная очистка целевой таблицы.

## Выбор основной категории

Если хотя бы одна категория объекта имеет `is_telecom=1`, выбор идёт только среди таких категорий. Сначала приоритет имеет подтип «Ремонт телефонов», затем порядок тегов:

1. `mobile_phone_repair`;
2. `mobile_phone`;
3. `telecommunication`, `telecom`;
4. `electronics_repair`;
5. `electronics`;
6. `computer`;
7. `repair`.

Приоритеты и описание хранятся в **`config/primary_selection.json`**. Чем раньше значение в списке, тем оно приоритетнее. Если телефонии нет, используется `other_tag_priority`. Неуказанные значения выбираются последними по алфавиту; перестановка входных строк не меняет результат. При переименовании уточняющих подтипов в `telecom.json` согласуйте соответствующие названия в `telecom_type_priority`.

| Поле | Значение |
|---|---|
| primary_tag | Единственный выбранный исходный тег; выдуманный тег вместо исходного не создаётся |
| primary_category | Его бизнес-категория |
| primary_subcategory | Его подкатегория |
| primary_osm_key / primary_osm_value | Точная исходная пара OSM выбранной категории |
| primary_reason | Как сработал приоритет: по подтипу телефонии, тегу телефонии, обычному тегу или алфавиту |
| all_tags | Полный список исходных тегов JSON-массивом, например `["electronics", "mobile_phone"]` |

`is_telecom` относится ко всему объекту. `telecom_type` и `telecom_evidence` в файле Teradata относятся к выбранной категории. Информация о сети остаётся общей для объекта и не теряется при выборе основного тега. Полные соответствия категорий сохранены в `classifications` общего `poi.csv`, а также в детальном реестре.

Исходные `tag`/`category` с объединёнными значениями через ` | ` в файле Teradata отсутствуют: вместо них используются отдельные `primary_*`. CSV использует UTF-8 BOM, `;`, признаки `1/0` и пустое значение для NULL. В Parquet признаки имеют boolean, даты — DATE. Перед загрузкой проверьте лимиты длин и Unicode; загрузчик не должен молча обрезать строки.

## Уникальность и обновления

Логический ключ и предлагаемый UNIQUE PRIMARY INDEX: **`(OSM_TYPE, OSM_ID)`**. Основная категория в ключ не входит. Поэтому смена `primary_tag` обновляет существующую строку через MERGE. `node/123` и `way/123` сохраняются отдельно: одинаковое число не означает один объект.

[teradata.sql](teradata.sql) описывает новую таблицу, staging, проверку дублей и MERGE. Старую таблицу с ключом `(OSM_TYPE, OSM_ID, TAG)` нужно мигрировать отдельно с сохранением данных, а не применять к ней новую схему автоматически. SQL не удаляет старую таблицу и не исполняется программой.

Загружайте **полный `poi_teradata.csv/parquet` успешного объектного экспорта**, а не категорийную `delta/`. Статусы и даты в нём сводятся из категорий, отдельная история изменения приоритетов не рассчитывается. Изменение экспортного справочника может поменять основную категорию при прежнем `record_status=UNCHANGED`; MERGE должен обновлять совпавшие ключи независимо от этого статуса. Хеш правил сохраняется в `object_export.primary_rules_sha256` отчёта запуска или `primary_rules_sha256` отчёта преобразования.

Для рабочего процесса:

1. Прочитать атомарный указатель успешного запуска, проверить источник, охват, границы и статус; preview и частичные данные использовать только для испытаний.
2. Очистить и заполнить staging для одного конкретного запуска; проверить ключи, число строк, типы и длины значений.
3. В транзакции сохранить историю с `RUN_ID`, выполнить MERGE по паре `(OSM_TYPE, OSM_ID)` и отметить запуск загруженным.
4. При повторной загрузке того же `RUN_ID` применять согласованную идемпотентность; при сбое выполнять rollback.

Отсутствие объекта в staging ничего не удаляет. Категорийный DELETED нельзя напрямую применять к объекту: у него могут оставаться другие категории. Для удаления объектов нужен отдельный контроль полного согласованного охвата и отсутствия всех категорий; автоматический объектный загрузчик/расчёт таких удалений здесь не заявлен. Региональная или неуспешная выгрузка не является основанием удалить данные всей страны.

## Применить новый приоритет без чтения PBF

```powershell
.\.venv\Scripts\python.exe -m poi_osm.objects "D:\parser\parser_osm\preview\20261110T213831-2af06975"
```

Будет создана новая папка `unique-...` с файлами для Teradata и общей объектной выгрузкой; прежние файлы и реестр не меняются. Для альтернативного справочника добавьте `--priority-config "D:\parser\my_priorities.json"`. В settings обычного запуска альтернативный путь задаётся полем `primary_selection` относительно `project_root`. Приоритеты применяются к сохранённой классификации; изменение самих тегов/телефонии требует повторной обработки PBF.

## Сокращённая выгрузка для загрузки

Полный внутренний `poi_teradata.csv` нужен для проверок и воспроизводимости. Фактические файлы загрузки с сокращённой схемой создаются отдельной командой в новой папке:

```powershell
.\.venv\Scripts\python.exe -m poi_osm.teradata_export "D:\osm_results\runs\<run_id>" --output "D:\osm_results\teradata"
```

Файл **`config/teradata_export.json`** содержит редактируемый список `fields` и формат ключа. По умолчанию исключены 19 согласованных полей. Остаются 16 колонок:

```text
osm_id, point_name, lon, lat, wkt, region_name,
primary_category, primary_subcategory, primary_osm_key, primary_osm_value,
is_telecom, telecom_type, is_chain, chain_name, update_date, record_status
```

`osm_id_format: "typed"` записывает **`node/123` / `way/123`** в `osm_id`; в Teradata это VARCHAR, а не числовая колонка. Уникальность сохраняется без отдельного `osm_type`. Если требуется исходное число, используйте `numeric_with_type` и добавьте `osm_type` в `fields`: одинаковые номера разных типов нельзя объединять. Пример схемы и MERGE для текстового ключа: [teradata_compact.sql](teradata_compact.sql). Он не меняет существующую таблицу и программно не исполняется.

Внутри `D:\osm_results\teradata\teradata-<timestamp>-<id>` находятся `poi_teradata.csv`, `poi_teradata.parquet`, региональные CSV с теми же сокращёнными колонками, `regions_index.csv`, зафиксированный `profile.json` и `summary.json`. В региональном индексе остаются коды регионов для навигации; в строках POI они удалены. Объекты без региона сохраняются отдельной частью и в общем файле. Метаданные, исключённые из загрузки, остаются в исходном production-реестре и полных внутренних файлах.

Экспорт проверяет уникальность ключей на диске, число строк CSV/Parquet, схему и региональные счётчики. Результат `file_checks_ok: true` относится к этим проверкам проекции; он не заменяет географическую проверку исходного запуска. Команда `poi_osm.audit` предназначена для полного внутреннего запуска, а не сокращённой папки. Изменение выходных колонок не требует чтения PBF и не влияет на последующую актуализацию полного реестра. Соединение с Teradata и загрузчик по-прежнему отдельно; история и удаления автоматически в СУБД не применяются.
